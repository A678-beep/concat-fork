# macOS 移植计划（星籁剪辑 0.5.0 → 0.6.0）

> 配套文档：[01-移植障碍清单.md](01-移植障碍清单.md)。本计划只覆盖"不依赖 Mac 的
> 准备工作"之后的真机落地；`main` 分支稳定构建不受影响，所有改动走
> `feat/macos-port-prep` 分支。
>
> 口径：**P0 编译并启动 → P1 核心剪辑可用 → P2 导出/工程包/插件 → P3 签名公证分发**。
> 每个阶段有明确验收，没在真机验证过的能力一律不算完成。

## 0. 现状一句话

工程本身是跨平台架构（上游 Concat 原生支持 macOS），本分支已完成**不依赖 Mac 的
全部准备**：障碍清单、平台模块抽取（`concat-host/src/tools.rs`）、`build.rs` 的
macOS 链接参数守卫、GitHub Actions 工作流、`.app`/`.dmg` 打包脚本、脚本可执行位
修复。**下一步必须有一台 Mac（或 GitHub macOS runner）才能继续**。

## 1. 阶段与工时

总工时约 **114 小时 ≈ 14.3 人天**（不含采购等待）；按 1 名熟悉本工程的 Rust 工程师
计，日历约 **3 周**（含 Mac 到货、Apple 账号审核）。

## 3. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 首次 macOS 编译失败（FFmpeg/whisper/onnxruntime 的 C 依赖、链接参数） | 高 | P0 延期 1–3 天 | 按上游 `.github/upstream-workflows/build-app.yml:220-420` 的步骤照抄；先跑 GitHub runner，不依赖本地 Mac 排错 |
| 账号登录在 macOS 的 TLS 被平台 WAF 重置（Windows 上 rustls/Schannel 被重置过，`docs/REBRAND.md` §4） | 中 | P1 核心企业功能延期 | 优先随包 OpenSSL 静态库（与 Windows 同形状），rustls 作退路；验收标准"macOS 登录成功率 100%" |
| 本地 AI 插件体系 Windows-only（内嵌 `python.exe`） | 高 | P2 范围蔓延 | 首版明确标注"macOS 暂不支持本地 AI 插件"，云端 AI 不受影响；单独立项再做 |
| VideoToolbox 编码差异（10-bit、Intel 回退、码率控制） | 中 | 导出质量问题 | P1-B 的导出矩阵作为准入门槛；保留 CPU 回退开关 |
| Apple 公证/证书流程等待 | 中 | 分发延期 | P3-A/B 提前启动，和 P1/P2 并行；先用 ad-hoc 内部测试 |
| Intel Mac 支持成本（ORT 1.23.2 只到 macOS 13.4、runner 慢 70 分钟） | 中 | 工时/CI 成本 | 与老板确认是否需要 Intel；企业客户多为 Apple Silicon，可先只发 arm64 |
| 构建时长/磁盘（fat LTO、60GB target） | 高 | 开发效率 | CI 用 rust-cache + FFmpeg 缓存（工作流已配）；本地固定一台构建机 |
| AGPL/第三方合规（FFmpeg LGPL、内嵌字体 Noto、模型许可） | 低 | 法务 | `.app/Contents/Resources/legal` 已随包 LICENSE/SOURCE_OFFER/THIRD_PARTY_NOTICES；保持 FFmpeg 不开 GPL |
| 改动影响 Windows 稳定构建 | 低 | 严重 | 所有改动：`#[cfg]` 守卫、新增文件、只在 macOS 执行的脚本；验收含 Windows `cargo check`（本轮已过）；CI 只在 GitHub macOS runner 上跑 |

## 4. 不破坏 Windows 的保证（本轮已落实）

1. 从 `main` 新开 `feat/macos-port-prep`，未合并前 `main` 不变；
2. Rust 改动全部是**新增文件**或**平台守卫**（`tools.rs` 为新增；`build.rs` 的
   macOS 链接参数由 `CARGO_CFG_TARGET_OS=macos` 守卫；三处 CLI 查找抽到平台模块，
   Windows 行为保持"exe 旁的 ffmpeg.exe/ffprobe.exe 优先"）；
3. CI 工作流只在 GitHub 的 `macos-15` / `macos-15-intel` runner 上运行；
4. 打包脚本只在 macOS 执行，Windows 的 Inno Setup 流程（`assets/windows/concat.iss`）
   一字未动；
5. 验收：Windows 侧 `cargo check -p concat` 通过；安装包可由既有
   `F:\concat\work\package-0.5.0.ps1` 路径原样产出（本分支未动其依赖）。

## 6. 推送状态与立即可执行的操作（不需要等 Mac）

**已推送**：`feat/macos-port-prep` 的非工作流部分（`tools` 平台模块、`build.rs`
macOS 栈守卫、`scripts/macos/package.sh`、5 个脚本可执行位、01/02 文档、
`.gitignore`）已经通过代理 `127.0.0.1:7890` 推到
<https://github.com/A678-beep/concat-fork>。

**阻塞**：`.github/workflows/macos-build.yml` 推不上去。本机系统凭据里的 GitHub
token 是经典 PAT，scope 只有 `repo`，GitHub 的拒绝原文是：

```text
! [remote rejected] feat/macos-port-prep -> feat/macos-port-prep
  (refusing to allow a Personal Access Token to create or update workflow
   `.github/workflows/macos-build.yml` without `workflow` scope)
```

这和 `docs/REBRAND.md` §2 记录的情况一致：当初上游工作流就是因为 fork 的 token
没有 `workflow` 权限才被挪进 `.github/upstream-workflows/` 的。解锁方式（任选一）：

1. 给 token 加 `workflow` scope（GitHub → Settings → Developer settings →
   Personal access tokens），然后在同一分支补推：
   ```bash
   cd F:/concat/src
   git push -c http.proxy=http://127.0.0.1:7890 -c https.proxy=http://127.0.0.1:7890 \
     origin feat/macos-port-prep
   ```
2. 让仓库 owner（或任何有 `workflow` 权限的账号）在网页上新建
   `.github/workflows/macos-build.yml`，内容取本分支工作区里的同名文件；
   本地 commit 已包含该文件，`git show HEAD:.github/workflows/macos-build.yml`
   可取。

推送成功后：GitHub → Actions → **macOS build** → Run workflow（或 `gh workflow
run macos-build.yml`）。

```bash
# 1. 本分支：Windows 侧验证（已跑通，见 01 文档 §2/§5）
cd F:/concat/src/src && cargo check -p concat

# 2. Mac 到货后本地跑同一套
cd <repo>/src && cargo build --profile app -p concat --target aarch64-apple-darwin
cd <repo> && bash scripts/macos/package.sh --target aarch64-apple-darwin
bash scripts/ci/smoke-macos.sh "src/target/macos-arm64/星籁剪辑.app"
```
